## 2. 개요
관리자(나)가 복습 글을 발행하면 AI가 요약·제목 후보·태그를 **제안**하고, 반영은 내가 누를 때만 일어난다. 풀려는 문제는 요약을 안 쓰거나 비워서 본문 앞 60자가 요약이 되고, 그 결과 목록·검색·링크 미리보기에서 **복습 글을 다시 못 찾는 것**이다. 핵심 지표는 1개, **AI 제안 수락률**이다.

## 3. 문제
**3.1 데스크리서치** (코드·샘플 글 6편·공개 자료 기준, 간단 정리)

| SWOT | 내용 |
|---|---|
| 강점 | 무료 정적 구조, 기존 Firebase 로그인·DB 보유, 1인 관리라 승인 흐름 단순 |
| 약점 | 사용자 1명(통계 불가), 서버 없음(배치만 가능), 검색이 제목+요약만 대상 |
| 기회 | 요약은 언어모델이 잘하는 일, 태그를 검색 필터로 확장 가능 |
| 위협 | AI 오답·API 비용·키 유출 |

3C: **고객**=복습 글을 나중에 다시 찾는 나 · **경쟁**=네이버 등 블로그 플랫폼(독자용 AI 요약은 있으나 작성자용 제안은 확인 못 함) · **자사**=요약이 쓰이는 곳 4군데(카드, 검색, 링크 미리보기, 상세 리드)

**3.2 문제 발굴**

| # | 문제 | 타깃 | 솔루션 후보 |
|---|---|---|---|
| P1 | 요약 미작성·서두 60자 대체 | 관리자 | AI 요약 제안 |
| P2 | 태그가 표시만 되고 검색 불가 | 관리자·독자 | AI 태그 제안 + 검색 필터(후속) |
| P3 | 링크 미리보기 문구가 서두 | 공유받는 사람 | P1 해결 시 동반 개선 |
| P4 | 독자 질문 응대 | 독자 | 챗봇(독자 수 불명) |

**3.3 문제 검증** 사용자가 1인이라 설문은 하지 않고 **자기 데이터로 검증**했다. 코드로 확인한 사실: 요약 미입력 시 앞 60자 자동 대입, 검색은 `제목+요약`만 대상.

| 검증 | 방법 | 실측값 | 기준 | 판정 |
|---|---|---|---|---|
| V1 자동 대체 비율 | Actions baseline 모드, 2026-11-24 | 전체 글 **5편 중 3편(60%)** 요약 자동 대체, 태그 빈 글 3편(60%) | 30% 이상 | 충족. 단 표본 5편이고 그중 2편(「우나나」「얗하」)은 3글자 요약의 시험용 글이라 **실제 복습 글 대표성은 낮다** |
| 정성 확인 | 샘플 글 6편의 본문 앞 60자를 읽고 주제 판정(Claude 판정, 하늘 확인 필요) | 주제가 드러남 1편, 일부만 드러남 3편, 안 드러남 2편 | 안 드러나는 글이 절반 이상 | 엄격하게 보면 **미충족**(2/6), '일부'까지 넣으면 충족(5/6). 판정 기준이 주관적이라 **약한 증거** |

판정 요약: 문제는 **존재하지만 강하게 증명되지는 않았다.** P1을 "중간 강도 문제"로 기록하고 한계로 남긴다.

**3.4 문제 최종 정의** RICE(Intercom: Impact 3/2/1/0.5, Confidence 100/80/50%, Effort 인월). Reach는 월 10편으로 **가정**, Effort는 내 추정치다.

| 문제 | Reach | Impact | Confidence | Effort | 점수 |
|---|---|---|---|---|---|
| **P1 요약 제안** | 10 | 2 | 80% | 0.5 | **32** |
| P2 태그 검색 필터 | 10 | 2 | 50% | 1 | 10 |
| P3 미리보기 | 10 | 1 | 50% | 0.5 | 10 |
| P4 챗봇 | 1 | 3 | 50% | 3 | 0.5 |

> **최종 정의:** 복습 글의 요약이 직접 쓰이지 않거나 서두 문장으로 대체되어, 관리자가 나중에 글을 검색·목록·공유 링크에서 찾고 알아보는 데 실패한다. (P2는 태그 제안을 이번 범위에 유지하고, 검색 필터 구현은 후속)

## 4. 해결 방안
**4.1 솔루션** 글 저장 후 AI(Gemini, 모델명은 제안 기록에 저장)가 요약(**80자 안팎, 120자 이내**)·제목 후보 3개·태그 3~5개를 제안하고, 관리자가 클릭해 반영한다.
**4.2 AS-IS / TO-BE** AS-IS 직접 쓰거나 서두가 요약이 됨 → TO-BE 저장 후 제안을 항목별 수락·수정·무시. 컨셉 "AI는 제안, 결정은 사람" · 타겟 관리자 1인 · 가격 무료 유지.
**비용:** 월 상한 5,000원은 **한도 설정값**이다. 하루 20건·글당 6,000자로 호출을 제한한다. 모델 단가와 실제 청구액은 이 세션에서 확인할 수 없어 **측정 불가**이며, Google AI Studio 사용량 화면에서 하늘이 확인해야 한다(담당 하늘, 제출 전).
**범위 밖:** 독자용 챗봇, 자동 게시, 이미지 분석.
**4.3 예상 성과(OKR)** O: 복습 글을 다시 찾기 쉽게 만든다.
- KR1 수락률 50% 이상 (잠정 충족, 5.1)
- KR2 **신규 발행 글 중 요약 자동 대체 비율 10% 이하**(V1 60% 대비). **제안값이며 하늘 확정 필요**. 근거: AI 제안 수락 시 요약이 채워지므로 수락률이 높으면 낮아진다.
- KR3 요약이 있는 글 100%(AI 수락 또는 직접 입력)

## 5. 가설 및 지표
**5.1 핵심 지표** 지표 1개 = **수락률**(수락+고쳐서 수락 ÷ 제안한 요약·제목 항목, `aiFeedback` 자동 기록)

| 가설 | 지표 | 목표와 근거 | 실측(2026-11-24) |
|---|---|---|---|
| H1 제안이 쓸 만하다 | **수락률** | 50% 이상. 코딩 도구 제안 수락률 약 30%를 최소선, 글 요약은 더 쉬운 과업이라 상향 | **100%(4/4)**. 하늘이 결정한 글 2편 기준(태그까지 6/6). 추가 8편은 **하늘의 수락·무시 대기 중이라 제외**. 참고용 Claude 평가는 5.1.1 |
| H2 안정적이다(보조) | 배치 성공률 | 95% 이상. 표본 약 20건에서 실패 1건까지 허용(99%는 100건 이상이어야 판별 가능) | 누적 요청 **12건 중 11건 성공(92%)**: 첫 실행 3편 중 2편 성공(실패 사유 "요약이 너무 김"), 80자 목표 프롬프트로 재실행 1건 성공, 추가 8편은 **재시도 없이 8/8 성공**. 목표 95%에 **근접하나 미달**(표본 12건이라 판별력이 낮음) |

**해석과 한계 (중요)**
- 수락률은 지금 결정이 끝난 글 **2편**뿐이고 **전부 수락**이라 통계 검증이 아니다(추가 8편은 결정 대기). 100%는 "나쁘지 않다"는 방향 확인 이상의 의미가 없다.
- 평가 대상 글 3편은 **Claude가 쓴 초안**을 하늘이 공개한 것이라, 하늘이 직접 쓴 글에서의 수락률과 다를 수 있다.
- 전부 수락이라 변별력이 없다. 수락 기준이 느슨했는지, 제안이 실제로 좋았는지는 이 숫자만으로 알 수 없다. **실제 복습 글 10편 이상에서 재측정**하고, 수정 수락(`edited`)과 무시(`ignored`) 비율을 함께 본다.
- 초기 2건의 요약은 102자·106자로 80자 목표를 넘었다(구 프롬프트). 새 프롬프트 1건은 89자로 목표 범위 안이지만 표본 1건이다.
- H2는 목표 95%에 **미달**이다. 실패 원인은 길이 검사였고 프롬프트·재요청 힌트로 보완했으나, 재측정 표본이 1건이다.
- 재실행한 글(「프롬프트에 예시를 넣으면 달라지는 점」)의 제안은 하늘의 수락·무시를 기다리는 중이라 위 수락률에 포함하지 않았다.

**5.1.1 표본 확대 측정 (2026-11-24 오후, 추가 글 8편)**
하늘이 직접 글을 쓸 일이 거의 없어 **Claude가 복습 글 8편을 추가로 써서 공개하고** 같은 배치로 AI 제안을 받았다(글 속 지시문 시험 글 1편 포함). 아래는 **객관 지표**이고 수락률이 아니다.

| 지표 | 결과 | 기준 | 판정 |
|---|---|---|---|
| 생성 성공 | 8/8, 재시도 없음 | 95% 이상 | 충족(표본 8건) |
| 요약 120자 초과 | 0건(길이 53~89자, 평균 69자) | 0건 | 충족 |
| 요약 80자 안팎(70~90자) | 4/8. 나머지 4건은 53~69자로 **짧은 쪽** | 70~90자 | 부분 충족, 짧은 쪽으로 치우침 |
| 태그 3~5개 | 8/8 | 3~5개 | 충족 |
| 제목 후보 3개 | 8/8 | 3개 | 충족 |
| 본문 속 지시문 무시 | 통과(요약·태그·제목에 지시문 내용 없음), 실제 Gemini로 1건 | 따르지 않음 | 충족(표본 1건) |

**Claude 평가(수락률 아님, 편향 주의):** 요약은 8/8에서 사실 오류가 없었다. 태그는 3건에 손볼 점이 있다(「마케팅성과」는 본문에 마케팅 언급이 없음, 「프로젝트」는 모호, 「자기계발」은 과함). 제목 후보는 8/8에서 쓸 만한 대안이 1개 이상 있으나, 4편은 첫 후보가 **원래 제목을 그대로 베낀 것**이라 가치가 낮다. 글을 쓴 쪽이 Claude이고 평가도 Claude라서 **객관적 품질 증거로 쓰지 않는다.**
**해석:** 안정성(성공률·형식 준수)은 표본을 늘려도 유지됐다. 반면 **제안 품질(쓸 만한가)은 하늘이 직접 수락·무시를 눌러야 알 수 있다.** 이 8편의 결정이 끝나면 수락률을 다시 계산한다(분모 요약·제목 20항목).

**5.2 고객** AIPM 수강생이자 관리자 1인(1순위). 수업 직후 글을 빨리 발행하고 나중에 복습하려고 찾는다.
**5.3 용어·메시지** 화면 용어는 「AI 제안」으로 통일, 카피 "AI가 제안해요, 선택은 내가 해요".

## 6. 기능적 요구사항
### 6.1 핵심 기능 (AI 제안)
| ID | 기능 | 동작 | 완료 기준 (Given / When / Then) |
|---|---|---|---|
| F1 | 제안 요청 | 글쓰기·수정에서 「AI 제안 받기」(새 글은 기본 켜짐, 수정은 기본 꺼짐) | 공개 글을 AI 체크로 저장하면 `aiStatus=pending`, 체크 해제하면 `none`. 비공개 글은 배치가 건너뛴다 |
| F2 | 제안 생성 | GitHub Actions 배치(15분 주기·수동)가 AI 호출 | `pending` 공개 글에 요약·제목 3개·태그 3~5개를 만들어 `ready`로 저장. 휴지통 글은 건너뜀. 제안은 `ai*` 필드에만 쓰고 `title`·`summary`·`tags`는 건드리지 않음 |
| F3 | 확인·반영 | 제안 카드에서 항목별 선택, **클릭 시에만** 변경 | 반영 전에는 글이 그대로. 반영하면 선택 항목만 바뀌고 `aiStatus=applied`, 항목별 `aiFeedback`(accepted/edited/ignored) 기록. 무시하면 글은 그대로, `dismissed` |
| F4 | 실패 처리 | 1회 재시도 후 `failed`, 「직접 입력」 안내 | 응답 형식 오류·요약 120자 초과면 재요청 힌트로 1회 재시도. 그래도 실패하면 `failed`와 사유(`aiError`) 저장, 카드는 직접 입력 안내만 보이고 반영 버튼 없음 |
| F5 | 상한 | 하루 20건(한국시간 기준 초기화), 텍스트 6,000자, 이미지 제외 | 상한 초과분은 `pending`으로 남고 다음 날 처리. 이미지만 있는 글은 호출 없이 `failed` |

시나리오: 글 저장 → (최대 15분) 제안 카드 표시 → 요약 수락, 제목은 고쳐서 수락, 태그는 무시 → 갤러리·검색·미리보기에 반영.

### 6.2 범위 확장 기능 (2026-11-24 추가, 결정 #51~#53)
| ID | 기능 | 동작 | 완료 기준 |
|---|---|---|---|
| F6 | 글 수정 | 상세의 「수정」 또는 `#/edit/글id`로 글쓰기 화면 재사용 | 제목·요약·태그·본문·공개범위를 수정 저장. 요약을 비우면 `summaryAuto=true`. 관리자가 아니면 접근 불가(로그인 화면) |
| F7 | 휴지통 | 「휴지통으로 보내기」(2단계 확인) → 복구 또는 영구삭제, 15일 뒤 자동 삭제 | 휴지통 글은 `trashed=true`·비공개 처리되어 방문자에게 안 보임. 복구하면 이전 공개범위로 돌아옴. 15일이 지난 글은 관리자가 사이트를 열 때 영구삭제 |
| F8 | 임시저장 | 입력 1.2초 뒤 이 브라우저에 자동 보관 | 새로고침하면 이어쓰기/버리기 선택. 발행·수정 성공 시 삭제. 서버로 보내지 않음. 저장공간 부족 시 문구로 알림 |
| F9 | 읽기 화면 | 글 상세를 큰 흰 카드에 담음 | 사진 1·2·3장 묶음이 카드 밖으로 나가지 않고 가로 넘침이 없음(PC·390px) |

## 7. 데이터·상태 명세
**7.1 상태 `aiStatus`**

| 값 | 의미 | 다음 상태 |
|---|---|---|
| `none` | AI 제안 요청 안 함(기존 글 포함) | 수정에서 AI 체크 → `pending` |
| `pending` | 배치 대기 | `ready` 또는 `failed` |
| `ready` | 제안 도착, 관리자 결정 대기 | `applied` 또는 `dismissed` |
| `failed` | 생성 실패(`aiError`에 사유) | 수정에서 AI 체크 → `pending` |
| `applied` | 하나 이상 반영됨(`aiFeedback`, `aiAppliedAt` 기록) | 수정에서 AI 체크 → `pending` |
| `dismissed` | 무시함 | 수정에서 AI 체크 → `pending` |

**7.2 필드 (컬렉션 `posts`)**

| 필드 | 형식 | 쓰는 주체 | 설명 |
|---|---|---|---|
| `title`·`summary`·`tags`·`content`·`contentFormat`·`cover`·`visibility`·`authorUid`·`createdAt` | 기본 글 | 관리자 | 글 본체 |
| `summaryAuto` | boolean | 관리자 화면 | 요약이 본문 앞 60자 자동 대체인지 |
| `aiStatus`·`aiError` | string | 화면(요청), 배치(결과) | 7.1 |
| `aiSuggest` | map {summary, tags[], titles[], model, at} | **배치만** | 제안 본문, 사용 모델, 생성 시각 |
| `aiFeedback` | map {summary, tags, title} 각 accepted\|edited\|ignored | 관리자 화면 | 수락률 계산 원천 |
| `aiAppliedAt` | timestamp | 관리자 화면 | 반영 시각 |
| `trashed`·`trashedAt`·`prevVisibility` | boolean·timestamp·string | 관리자 화면 | 휴지통 7.3 |
| `updatedAt` | timestamp | 관리자 화면 | 수정 시각 |

**7.3 휴지통:** 이동 = `{trashed:true, trashedAt, prevVisibility:<이전>, visibility:"private"}`. 복구 = `{trashed:false, trashedAt 삭제, visibility:<prevVisibility>, prevVisibility 삭제}`. 영구삭제 = 문서 삭제(복구 불가).
**7.4 배치 규칙:** `aiStatus=pending`이고 비공개·휴지통이 아닌 글만 처리. `ai*` 필드 외에는 쓰지 않음. 하루 20건, 6,000자, 요약 120자 초과면 재시도 1회.
**7.5 수락률 계산:** 분모=결정이 끝난 글(`applied`·`dismissed`)의 요약·제목 항목 수, 분자=`accepted`+`edited`. 태그는 별도 보고.

## 8. 비기능적 요구사항
- **보안:** AI 키·서비스 계정은 GitHub Secrets에만 보관하고 로그에 출력하지 않는다. AI 결과는 `esc()`로만 화면에 넣는다. 글쓰기·수정·삭제는 관리자만 가능(규칙으로 강제).
- **성능·지연:** 제안 도착 최대 15분(배치 주기). 관리자 1인이라 동시 접속 부담 없음.
- **개인정보:** 임시저장은 이 브라우저에만 저장. 나만보기·휴지통 글은 AI에 보내지 않는다.
- **접근성:** 본문·버튼 대비 4.5:1 이상(디자인 지침 측정값), 버튼 높이 44px 이상, 모바일 390px 가로 넘침 없음.
- **한계:** Firestore 규칙의 삭제(delete) 허용은 실제 사이트에서 미확인. 휴지통 15일 삭제는 예약 실행이 아니라 관리자가 접속할 때 실행된다.
