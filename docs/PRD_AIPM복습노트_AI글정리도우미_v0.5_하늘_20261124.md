# PRD · AIPM 복습 노트 「AI 글 정리 도우미」

## 1. 기본 정보
**문서 버전** v0.5 · **작성일** 2026-11-24

## 2. 개요
관리자(나)가 복습 글을 발행하면 AI가 요약·제목 후보·태그를 **제안**하고, 반영은 내가 누를 때만 일어난다. 풀려는 문제는 요약을 안 쓰거나 비워서 본문 앞 60자가 요약이 되고, 그 결과 목록·검색·링크 미리보기에서 **복습 글을 다시 못 찾는 것**이다. 핵심 지표는 1개, **AI 제안 수락률**이다.

## 3. 문제
**3.1 데스크리서치** (코드·샘플 글 6편·공개 자료 기준, 간단 정리)

| SWOT | 내용 |
|---|---|
| 강점 | 무료 정적 구조, 기존 Firebase 로그인·DB 보유, 1인 관리라 승인 흐름 단순 |
| 약점 | 사용자 1명(통계 불가), 서버 없음(배치만 가능), 검색이 제목+요약만 대상 |
| 기회 | 요약은 언어모델이 잘하는 일, 태그를 검색 필터로 확장 가능 |
| 위협 | AI 오답·API 비용·키 유출 |

3C: **고객**=복습 글을 나중에 다시 찾는 나 · **경쟁**=네이버 등 블로그 플랫폼(독자용 AI 요약은 있으나 작성자용 제안은 확인 못 함) · **자사**=요약이 쓰이는 곳 4군데(카드, 검색, 링크 미리보기, 상세 리드)

**3.2 문제 발굴**

| # | 문제 | 타깃 | 솔루션 후보 |
|---|---|---|---|
| P1 | 요약 미작성·서두 60자 대체 | 관리자 | AI 요약 제안 |
| P2 | 태그가 표시만 되고 검색 불가 | 관리자·독자 | AI 태그 제안 + 검색 필터(후속) |
| P3 | 링크 미리보기 문구가 서두 | 공유받는 사람 | P1 해결 시 동반 개선 |
| P4 | 독자 질문 응대 | 독자 | 챗봇(독자 수 불명) |

**3.3 문제 검증** 사용자가 1인이라 설문은 하지 않고 **자기 데이터로 검증**한다(3.3.1). 코드로 확인한 사실: 요약 미입력 시 앞 60자 자동 대입, 검색은 `제목+요약`만 대상. 샘플 6편 모두 앞 60자가 서두·경위 문장이었다(통계 아님).

| 검증 | 방법 | 실측값 | 문제가 실재한다는 기준(근거) |
|---|---|---|---|
| V1 자동 대체 비율 | Actions baseline 모드 | **(미정)** | 30% 이상 (제안 수락률이 보통 20~33%인 점을 감안, 최소 3분의 1 가까이 해당되어야 개선 여지) |
| 정성 확인 | 샘플 글 6편의 자동 60자를 읽고 주제가 드러나는지 판정 | 6편 중 **(미정)**편 | 주제가 드러나지 않는 글이 절반 이상 |

사용자가 1인이라 외부 테스트(여러 명 조사)는 하지 않는다. **V1이 기준에 못 미치면 P1을 "약한 문제"로 기록**하고 한계로 남긴다.

**3.4 문제 최종 정의** RICE(Intercom: Impact 3/2/1/0.5, Confidence 100/80/50%, Effort 인월). Reach는 월 10편으로 **가정**, Effort는 내 추정치다.

| 문제 | Reach | Impact | Confidence | Effort | 점수 |
|---|---|---|---|---|---|
| **P1 요약 제안** | 10 | 2 | 80% | 0.5 | **32** |
| P2 태그 검색 필터 | 10 | 2 | 50% | 1 | 10 |
| P3 미리보기 | 10 | 1 | 50% | 0.5 | 10 |
| P4 챗봇 | 1 | 3 | 50% | 3 | 0.5 |

> **최종 정의:** 복습 글의 요약이 직접 쓰이지 않거나 서두 문장으로 대체되어, 관리자가 나중에 글을 검색·목록·공유 링크에서 찾고 알아보는 데 실패한다. (P2는 태그 제안을 이번 범위에 유지하고, 검색 필터 구현은 후속)

## 4. 해결 방안
**4.1 솔루션** 글 저장 후 AI가 요약(120자 이내)·제목 후보 3개·태그 3~5개를 제안하고, 관리자가 클릭해 반영하게 한다.
**4.2 AS-IS / TO-BE** AS-IS 직접 쓰거나 서두가 요약이 됨 → TO-BE 저장 후 제안을 항목별 수락·수정·무시. 컨셉 "AI는 제안, 결정은 사람" · 타겟 관리자 1인 · 가격 무료 유지(월 비용 상한 5,000원, 단가 **(미정)**) · 범위 밖: 독자용 챗봇, 자동 게시, 이미지 분석.
**4.3 예상 성과(OKR)** O: 복습 글을 다시 찾기 쉽게 만든다. KR1 수락률 50% 이상 · KR2 서두 자동 대체 글 비율을 V1 대비 감소(목표 **(미정)**) · KR3 요약이 있는 글 100%

## 5. 가설 및 지표
**5.1 핵심 지표** 지표 1개 = **수락률**(수락+고쳐서 수락 ÷ 제안한 요약·제목 항목, `aiFeedback` 자동 기록)

| 가설 | 지표 | 목표와 근거 | 실측 |
|---|---|---|---|
| H1 제안이 쓸 만하다 | **수락률** | 50% 이상. 코딩 도구 제안 수락률 약 30%를 최소선, 글 요약은 더 쉬운 과업이라 상향 | (미정) |
| H2 안정적이다(보조) | 배치 성공률 | 95% 이상. 표본 약 20건에서 실패 1건까지 허용(99%는 100건 이상이어야 판별 가능) | (미정) |

표본이 작아 통계 검증이 아니라 방향 확인이다.
**5.2 고객** AIPM 수강생이자 관리자 1인(1순위). 수업 직후 글을 빨리 발행하고 나중에 복습하려고 찾는다.
**5.3 용어·메시지** 화면 용어는 「AI 제안」으로 통일, 카피 "AI가 제안해요, 선택은 내가 해요".

## 6. 기능적 요구사항
| ID | 기능 | 동작 |
|---|---|---|
| F1 | 제안 요청 | 글쓰기 「AI 제안 받기」(기본 켜짐) → 저장 시 `aiStatus:pending` |
| F2 | 제안 생성 | GitHub Actions 배치(15분 주기·수동)가 AI 호출 → `ready`/`failed` |
| F3 | 확인·반영 | 제안 카드에서 항목별 선택, **클릭 시에만** 제목·요약·태그 변경 |
| F4 | 실패 처리 | 1회 재시도 후 `failed`, 「직접 입력」 안내 |
| F5 | 상한 | 하루 20건, 텍스트 6,000자, 이미지 제외 |

시나리오: 글 저장 → (최대 15분) 제안 카드 표시 → 요약 수락, 제목은 고쳐서 수락, 태그는 무시 → 갤러리·검색·미리보기에 반영.

## 7. 비기능적 요구사항
키(AI·서비스 계정)는 GitHub Secrets에만 보관·로그 출력 금지. AI 결과는 `esc()`로만 화면 삽입. 배치는 `ai*` 필드만 쓰기. 제안 지연 최대 15분. 동시 접속 부담 없음(정적 사이트, 관리자 1인).

## 8. 디자인 요구사항
기존 디자인 시스템(`docs/design-system.md`)의 색·간격만 사용, 제안 카드는 mint 톤, 버튼 높이 44px 이상. 프로토타입 = 배포 블로그 URL(위 링크).

## 9. 출시 및 운영 전략
범위: F1~F5. 방식: 기존 GitHub Pages + `.github/workflows/ai-suggest.yml`. 테스트: 배치 단위 테스트(13건)·화면 시험을 11/25 오전 `docs/TEST_*.md`로 정리.

| 리스크 | 대응 |
|---|---|
| Firestore 규칙이 관리자 수정을 막을 수 있음(미확인) | 콘솔에서 확인·적용, 거부 시 화면 안내 |
| 서비스 계정 키 유출 | Secrets만 사용 |
| AI 오답·글 속 지시문 | 자동 반영 없음, 프롬프트에서 지시문 무시 |
| **문제 자체가 약할 수 있음** | V1·정성 확인 결과를 그대로 기록 |
