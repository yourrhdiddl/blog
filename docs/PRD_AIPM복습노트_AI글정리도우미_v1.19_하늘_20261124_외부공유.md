## 2. 개요

**한 줄 요약:** 글을 올릴 때마다 요약·제목·태그를 직접 쓰기 번거로워 비우게 되는 문제를, AI가 초안을 제안하고 관리자는 확인만 하는 방식으로 줄인다.

**1) 문제**

- **누가:** AIPM 수업을 듣고 복습 글을 올리는 관리자(나) 1명.
- **무슨 일이 있나:** 수업 직후 빨리 올리느라 요약·태그를 비우거나 한두 글자만 적는다. 실제로 글 5편 중 3편(60%)의 요약이 비어 있었다.
- **그래서 어떻게 되나:** 비운 요약 자리에 본문 앞 60자가 자동으로 들어가, 나중에 목록·검색·링크 미리보기에서 어떤 글인지 알아보기 어렵다. 이 불편이 얼마나 큰지는 아직 약한 근거다(3.3절).

**2) 해결**

- 글을 저장하면 AI가 요약(80자 안팎)·제목 후보 3개·태그 3~5개를 **제안**한다.
- 반영은 관리자가 누를 때만 일어난다. 항목마다 그대로 수락, 고쳐서 수락, 무시 중에서 고른다.
- 이 기능은 **"매번 직접 쓰는 수고"를 줄이는 편의 기능**이다. 글을 찾기 쉬워지는 것은 그 부수 효과로 본다.

**3) 성공 판단**

- 핵심 지표는 **AI 제안 수락률**이다.
- **수락률이란:** AI가 제안한 요약·제목 중 관리자가 그대로 또는 고쳐서 쓴 비율이다.
- **쉽게 말해:** 관리자(나)가 글을 쓸 때마다 요약·제목을 계속 직접 쓰는지, AI 제안을 받아 쓰는지를 본다. 높을수록 직접 쓰는 수고가 줄었다는 뜻이다.
- **목표와 현재:** 목표 50% 이상, 현재 77%(17/22). 방향 확인 수준이다(5.1절).
- **주의:** 수락률이 높다고 요약이 좋다는 뜻은 아니다. 무시한 경우 직접 썼는지 비웠는지도 이 지표로는 알 수 없어, 비우는 비율(M11)을 5.1.2절에서 따로 본다.

## 3. 문제
**3.1 데스크리서치** (코드·샘플 글 6편·공개 자료 기준, 간단 정리)

| SWOT | 내용 |
|---|---|
| 강점 | 무료 정적 구조, 기존 Firebase 로그인·DB 보유, 1인 관리라 승인 흐름 단순 |
| 약점 | 사용자 1명(통계 불가), 서버 없음(배치만 가능), 검색이 제목+요약만 대상 |
| 기회 | 요약은 언어모델이 잘하는 일, 태그를 검색 필터로 확장 가능 |
| 위협 | AI 오답·API 비용·키 유출 |

3C: **고객**=복습 글을 나중에 다시 찾는 나 · **경쟁**=네이버 등 블로그 플랫폼(독자용 AI 요약은 있으나 작성자용 제안은 확인 못 함) · **자사**=요약이 쓰이는 곳 4군데(카드, 검색, 링크 미리보기, 상세 리드)

**3.2 문제 발굴**

| # | 문제 | 타깃 | 솔루션 후보 |
|---|---|---|---|
| P1 | 요약·제목·태그를 매번 직접 쓰기 번거로워 비움(결과: 서두 60자 대체) | 관리자 | AI 요약·제목·태그 제안 |
| P2 | 태그가 표시만 되고 검색 불가 | 관리자·독자 | AI 태그 제안 + 검색 필터(후속) |
| P3 | 링크 미리보기 문구가 서두 | 공유받는 사람 | P1 해결 시 동반 개선 |

**3.3 문제 검증**

사용자가 1인이라 설문 대신 **자기 데이터로 검증**했다. 코드로 확인한 사실은 두 가지다.

- 요약을 비우면 본문 앞 60자가 자동으로 들어간다.
- 검색은 `제목+요약`만 본다.

| 검증 | 방법 | 실측값 | 기준 | 판정 |
|---|---|---|---|---|
| V1 자동 대체 비율 | Actions baseline 모드, 2026-11-24 | 5편 중 **3편(60%)** 자동 대체, 태그 빈 글 3편(60%) | 30% 이상 | 충족(약한 근거) |
| 정성 확인 | 샘플 6편의 앞 60자를 읽고 주제 판정(Claude 판정, 하늘 확인 필요) | 드러남 1편, 일부 3편, 안 드러남 2편 | 안 드러남이 절반 이상 | 엄격히 **미충족**(2/6), '일부'까지 넣으면 충족(5/6) |

**왜 약한 근거인가**

- V1: 표본 5편 중 2편(「우나나」「얗하」)이 3글자 요약의 시험용 글이라 실제 복습 글 대표성이 낮다.
- 정성 확인: 판정 기준이 주관적이다.

**판정 요약:** 문제는 **존재하지만 강하게 증명되지는 않았다.** P1을 "중간 강도 문제"로 기록하고 한계로 남긴다.

**3.4 문제 최종 정의** RICE(Intercom: Impact 3/2/1/0.5, Confidence 100/80/50%, Effort 인월). Reach는 월 10편으로 **가정**, Effort는 내 추정치다.

| 문제 | Reach | Impact | Confidence | Effort | 점수 |
|---|---|---|---|---|---|
| **P1 요약 제안** | 10 | 2 | 80% | 0.5 | **32** |
| P2 태그 검색 필터 | 10 | 2 | 50% | 1 | 10 |
| P3 미리보기 | 10 | 1 | 50% | 0.5 | 10 |
| P4 챗봇 | 1 | 3 | 50% | 3 | 0.5 |

> **최종 정의**
>
> - **누가:** 수업 직후 복습 글을 올리는 관리자(나).
> - **어떤 상황에서:** 빨리 올리느라 요약·태그를 직접 쓰기 번거로워 비우거나 한두 글자만 적는다.
> - **무슨 일이 생기나:** 비운 요약 자리에 본문 앞 60자가 들어간다. 2주 뒤 복습할 때 ① 목록 카드로 글을 알아보기 어렵고 ② 검색(제목+요약만 대상)에서 본문 속 단어와 태그로는 못 찾고 ③ 공유 링크 미리보기에 서두 문장이 보인다.
> - **얼마나:** 요약 자동 대체 5편 중 3편(60%), 태그 빈 글 5편 중 3편(60%), 현재 공개 글 6편 중 3편의 요약이 3자·3자·14자.
> - **범위:** P2(태그 검색 필터)는 후속. 태그 제안은 이번 범위에 유지한다.

**3.5 문제 시나리오와 실데이터 근거 (v1.2 신설)**

**시나리오(가정, 하늘 확인 필요):**

1. 수업이 끝난 직후 10분 안에 글을 올린다.
2. 요약 칸은 비워 둔다. 저장하면 본문 첫 60자가 요약이 된다(코드 확인).
3. 2주 뒤 시험 전에 목록을 훑는다. 카드 두 줄이 "오늘은 ○○를 배웠다" 같은 서두라 어떤 글인지 못 알아본다.
4. 기억나는 단어(예: 지표 이름)로 검색해도 제목·요약에 없으면 결과가 없다.

| 어디서 | 지금 동작 | 실데이터 | 판정 |
|---|---|---|---|
| 목록 카드 | 요약 2줄을 보여 줌 | 공개 글 6편 중 3편의 요약이 "우사기"(3자), "으아아"(3자), "굵은 빨강 큰 글씨 테스트"(14자). 모두 시험용 글이라 **실제 복습 글의 비율은 모름** | 시험용이지만 "비워 두면 이렇게 남는다"는 증거 |
| 검색 | 제목+요약만 대상, 태그·본문은 제외(코드 확인) | AI 제안이 반영된 글 3편의 태그 13개 중 **7개(54%)**가 제목·요약에 없는 단어(예: 「개발노트」「지표설정」「기획」「프로덕트」「인공지능」「작성법」「AI평가」)라 이 단어로는 못 찾는다 | 태그를 달아도 **검색에는 쓰이지 않음**(P2) |
| 기준값 V1 | 요약 미입력 시 앞 60자 대입 | 전체 5편 중 3편(60%) 자동 대체, 태그 빈 글 3편(60%) | 표본 5편이라 약한 근거 |
| 정성 확인 | 앞 60자를 읽고 주제 판정 | 6편 중 안 드러남 2편, 일부만 3편, 드러남 1편 | 판정이 주관적이라 약한 근거 |
| 반례 | 요약이 서두로 대체돼도 주제가 드러나는 글 | AI 반영 글 3편의 본문 앞 60자는 모두 주제를 드러냄(예: "AI 기능을 평가할 때 정확도 하나만 보면…") | **문제가 모든 글에서 생기지는 않음.** 서두가 도입 문장일 때만 문제 |

**문제가 아닌 것(범위 밖):** 글 내용의 품질, 독자 수(사용자 1명이라 측정 불가), 사진 업로드 속도.

|---|---|---|---|
| 요약이 직접 쓰였거나 AI 제안으로 채워진 글 | 90% 이상 | AI 처리 글 82%(9/11) | M10 |

## 4. 해결 방안
**4.1 솔루션** 글 저장 후 AI(기본 Gemini, Claude 키로 바꿔 쓸 수 있고 막히면 Gemini로 자동 복귀, 사용한 모델명은 제안 기록에 저장)가 요약(**80자 안팎, 120자 이내**)·제목 후보 3개·태그 3~5개를 제안하고, 관리자가 클릭해 반영한다.
**4.2 AS-IS / TO-BE**

- **AS-IS:** 직접 쓰거나 서두가 요약이 된다.
- **TO-BE:** 저장 후 제안을 항목별로 수락·수정·무시한다.
- **컨셉:** "AI는 제안, 결정은 사람" · **타겟:** 관리자 1인 · **가격:** 무료 유지
- **범위 밖:** 독자용 챗봇, 자동 게시, 이미지 분석

**비용**

- **한도(설정값):** 월 상한 5,000원, 하루 20건, 글당 6,000자. 실제 청구액은 측정하지 못했다(AI Studio 사용량 화면은 하늘 확인 필요).
- **단가(추정):** 제3자 집계 기준 gemini-3.5-flash-lite는 입력 100만 토큰당 약 0.30달러, 출력 약 2.50달러. Google 공식 가격표에서는 이 모델 항목을 직접 확인하지 못했다(참고용).
- **최악의 달 계산:** 월 600건 × 건당 입력 4,000토큰·출력 1,000토큰 = 입력 240만·출력 60만 토큰 ≈ 2.2달러 ≈ **약 3,200원**(1달러 1,450원 가정). 상한 5,000원 안이다.
- 무료 키 사용 시 실제 청구는 0원일 수 있다.

**4.3 예상 성과(OKR)** O: 복습 글을 다시 찾기 쉽게 만든다.
- KR1 수락률 50% 이상 (**충족 77%, 표본 한계 있음**, 5.1)
- KR2 **신규 발행 글 중 요약 자동 대체 비율 10% 이하**(V1 60% 대비). **하늘 확정(2026-11-24)**. 근거: AI 제안 수락 시 요약이 채워지므로 수락률이 높으면 낮아진다.
- KR3 요약이 있는 글 100%(AI 수락 또는 직접 입력)

## 5. 가설 및 지표
**5.1 핵심 지표** 지표 1개 = **AI 제안 수락률**

- **정의:** (그대로 수락 + 고쳐서 수락) ÷ AI가 제안한 요약·제목 항목. `aiFeedback`으로 자동 기록한다.
- **쉽게 말해:** 관리자(나)가 글을 쓸 때마다 요약·제목을 계속 직접 쓰는지, AI 제안을 받아 쓰는지를 본다. 높을수록 직접 쓰는 수고가 줄었다는 뜻이다.
- **한계:** 수락률이 높다고 요약이 좋다는 뜻은 아니고, 무시한 경우 직접 썼는지 비웠는지는 이 지표로 알 수 없다. 비우는 비율은 M11(5.1.2절)로 따로 본다.

| 가설 | 지표 | 목표 | 실측(2026-11-24) | 판정 |
|---|---|---|---|---|
| H1 제안이 쓸 만하다 | **수락률** | 50% 이상(코딩 도구 제안 수락률 약 30%를 최소선으로 보고, 글 요약은 더 쉬워 상향) | **77%**(17/22) | **충족** |
| H2 안정적이다(보조) | 배치 성공률 | 95% 이상(표본 약 20건에서 실패 1건까지 허용, 99%는 100건 이상이어야 판별 가능) | **92%**(11/12) | **미달**(근접) |

> **수락률 77%를 읽는 법**
>
> - **말할 수 있는 것:** 이 기능이 낸 제안은 대체로 받아들일 만했다(22항목 중 17). 목표 50%를 넘었으므로 "계속 개선해 볼 가치가 있다"는 방향은 지지한다.
> - **말할 수 없는 것:** 하늘님이 직접 쓴 글에서도, 다른 사용자에게도 77%가 나온다는 것은 말할 수 없다. 평가한 글 11편이 모두 Claude가 쓴 글이고 평가자는 1명이다.
> - **숫자가 가볍게 나올 수 있는 이유:** 고쳐서 수락이 0건이라 "그대로 눌렀다"와 "고치기 귀찮았다"를 구분할 수 없다. 반대로 무시 5항목에는 직접 쓰려고 무시한 경우와 안 쓰고 비운 경우가 섞여 있다.
> - **그래서 보고 문장:** "Claude가 쓴 글 11편 기준 수락률 77%(17/22), 사용자 1명이라 방향 확인 수준"으로 쓰고, 단독 성과로 인용하지 않는다.
> - **다음 측정:** 하늘님이 직접 쓴 글이 쌓이면 `edited`·`ignored` 비율과 함께 다시 잰다.

**수락률 17/22의 내역:** 결정한 글 11편 × 요약·제목 2항목 = 22항목 중 수락 17, 고쳐서 수락 0, 무시 5. 태그는 11편 중 9편 수락(82%)이라 별도 보고한다.

**성공률 11/12의 내역:** 첫 실행 3편 중 2편 성공(실패 사유 "요약이 너무 김") → 80자 목표 프롬프트로 재실행 1건 성공 → 추가 8편은 재시도 없이 8/8 성공.

**해석과 한계 (중요)**

수락률

- **방향 확인일 뿐이다.** 77%는 목표 50%를 넘지만 표본이 작고 사용자가 1명이라 통계 검증이 아니다.
- **글을 Claude가 썼다.** 평가한 11편은 모두 Claude가 쓴 초안(하늘이 공개한 3편 + Claude가 추가한 8편)이라, 하늘이 직접 쓴 글의 수락률과 다를 수 있다.
- **고쳐서 수락(`edited`)이 0건이다.** 그대로 받았다는 뜻일 수도, 고치기 귀찮아 눌렀다는 뜻일 수도 있어 품질을 단정할 수 없다. 직접 쓴 글이 쌓이면 `edited`·`ignored` 비율과 함께 재측정한다.
- **무시 5항목의 내역:** 2편은 요약·태그·제목 모두 무시, 1편은 제목만 무시했다.
- **포함된 특수 글:** 재실행한 글(구 「프롬프트에 예시를 넣으면 달라지는 점」, 현재 「원하는 결과물을 얻는 프롬프트 작성 팁」)과 글 속 지시문 시험 글(현재 「복습 노트 업로드 가이드」)도 수락되어 포함했다. 제안에 지시문 내용이 없음은 5.1.1절에서 확인했다.

성공률·요약 길이

- H2는 목표 95%에 **미달**이다. 실패 원인은 길이 검사였고 프롬프트·재요청 힌트로 보완했으나 재측정 표본이 적다.
- 초기 2건의 요약은 102자·106자로 80자 목표를 넘었다(구 프롬프트). 새 프롬프트 1건은 89자로 목표 범위 안이지만 표본 1건이다.

**5.1.1 표본 확대 측정 (2026-11-24 오후, 추가 글 8편)**
하늘이 직접 글을 쓸 일이 거의 없어 **Claude가 복습 글 8편을 추가로 써서 공개하고** 같은 배치로 AI 제안을 받았다(글 속 지시문 시험 글 1편 포함). 아래는 **객관 지표**이고 수락률이 아니다.

| 지표 | 결과 | 기준 | 판정 |
|---|---|---|---|
| 생성 성공 | 8/8, 재시도 없음 | 95% 이상 | 충족(표본 8건) |
| 요약 120자 초과 | 0건(길이 53~89자, 평균 69자) | 0건 | 충족 |
| 요약 80자 안팎(70~90자) | 4/8. 나머지 4건은 53~69자로 **짧은 쪽** | 70~90자 | 부분 충족, 짧은 쪽으로 치우침 |
| 태그 3~5개 | 8/8 | 3~5개 | 충족 |
| 제목 후보 3개 | 8/8 | 3개 | 충족 |
| 본문 속 지시문 무시 | 통과(요약·태그·제목에 지시문 내용 없음), 실제 Gemini로 1건 | 따르지 않음 | 충족(표본 1건) |

**Claude 평가(수락률 아님, 편향 주의):** 요약은 8/8에서 사실 오류가 없었다. 태그는 3건에 손볼 점이 있다(「마케팅성과」는 본문에 마케팅 언급이 없음, 「프로젝트」는 모호, 「자기계발」은 과함). 제목 후보는 8/8에서 쓸 만한 대안이 1개 이상 있으나, 4편은 첫 후보가 **원래 제목을 그대로 베낀 것**이라 가치가 낮다. 글을 쓴 쪽이 Claude이고 평가도 Claude라서 **객관적 품질 증거로 쓰지 않는다.**
**해석:** 안정성(성공률·형식 준수)은 표본을 늘려도 유지됐다. 반면 **제안 품질(쓸 만한가)은 하늘이 직접 수락·무시를 눌러야 알 수 있다.** 이 8편의 결정은 끝났고, 위 5.1절 수락률(11편 22항목)에 반영했다. 8편만 보면 요약·제목 16항목 중 수락 11, 무시 5이다.

**5.1.2 지표 체계 (2026-11-24 확장, 하늘 요청)**
핵심 지표는 수락률 1개로 두되, 수락률만으로는 "왜 높은지"와 "부작용은 없는지"를 알 수 없어 아래를 함께 본다. 모든 실측은 `aiFeedback`·`aiStatus`·`aiSuggest`와 배치 실행 기록에서 계산하며, 측정 못 한 칸은 "미측정"으로 둔다.

| 구분 | 지표 | 정의 | 목표 | 실측(2026-11-24) |
|---|---|---|---|---|
| **핵심** | M1 수락률 | (수락+고쳐서 수락) ÷ 결정 끝난 글의 요약·제목 항목 | 50%↑ | **77%** (17/22) |
| 항목별 | M2 요약 수락률 | 요약 accepted+edited ÷ 결정 글 수 | 참고 | 82% (9/11) |
| 항목별 | M3 제목 수락률 | 같은 방식, 제목 | 참고 | 73% (8/11). 첫 후보가 원제를 베낀 경우가 8편 중 4편(v1.8에서 지시문·코드로 줄임, 재측정 전) |
| 항목별 | M4 태그 수락률 | 같은 방식, 태그(M1 분모에는 불포함) | 참고 | 82% (9/11) |
| 사용 방식 | M5 고쳐서 수락 비율 | edited ÷ 수락 항목 | 참고(0%는 "그대로 쓴다" 또는 "고치기 귀찮다") | 0% (0/17) |
| 사용 방식 | M6 전체 무시율 | 요약·제목·태그를 모두 무시한 글 ÷ 결정 글 | 20% 이하 | 18% (2/11) |
| 보조(안정성) | M7 배치 성공률 | 성공 요청 ÷ 전체 요청 | 95%↑ | 92% (11/12), **미달** |
| 보조(품질) | M8 요약 길이 준수 | 전달된 제안 중 120자 이하 | 100% | 100% (11/11 전달분. 실패 1건은 길이 검사에서 걸러져 미전달) |
| 보조(품질) | M9 80자 안팎(70~90자) 비율 | 표본 8편 | 참고 | 50% (4/8), 짧은 쪽으로 치우침 |
| 효과 | M10 요약 반영 글 비율 | AI 처리 글 중 요약이 AI 제안으로 채워진 글 | KR3 | 82% (9/11) |
| 효과 | M11 요약 자동 대체 비율 | 신규 글 중 서두 60자가 요약이 된 글(**아래 정의 주의**) | KR2 10% 이하 | **미측정**(신규 글 없음) |
| 가드레일 | G1 지시문 주입 성공 | 본문 속 지시를 제안이 따른 건수 | 0건 | 0건 (시험 1건) |
| 가드레일 | G2 사실 오류 | Claude 평가 요약 사실 오류 글 수 | 0편 | 0/8 (편향 주의) |
| 가드레일 | G3 일일 호출 수 | 하루 AI 호출 | 20건 이하 | 상한으로 강제(실측 일별 기록 없음, **미측정**) |
| 지연 | M12 제안 도착 시간 | 저장→`ready` | 수동 실행 후 1분 이내(예약은 보장하지 않음) | **미측정**(예약은 약 15시간에 1회(#9)만 실행돼 불규칙하다. 확실한 방법은 대기 카드의 「지금 AI 제안 받기」로 연 수동 실행이며 1회 약 20~50초) |

**지표 정의 주의 (실데이터에서 발견):** 제안을 수락해도 `summaryAuto`가 `true`로 남는다(공개 글 3편에서 확인: 요약이 AI 제안으로 바뀌었는데도 `summaryAuto=true`). 그대로 세면 M11이 부풀려지므로 **M11은 `summaryAuto=true`이면서 `aiFeedback.summary`가 accepted·edited가 아닌 글**로 계산한다. v1.6에서 화면이 요약을 반영할 때 `summaryAuto`를 `false`로 바꾸도록 고쳤다. 이미 수락한 기존 글은 값이 그대로이므로 위 계산 방식을 기존 글에 계속 쓴다.
**아직 없는 것:** 독자 측 지표(검색 성공률, 클릭), 시간 절감. 사용자 1명이라 의미 있게 재기 어려워 이번 범위에서 뺐다.

**5.1.3 시연 글 10개 객관 지표와 공개 데이터 점검 (2026-11-25 오후)**
수락률이 아니라 **제안의 형식·길이 지표**다. 비로그인 상태에서 Firestore 공개 읽기(공개 글만 읽힘)로 시연 글 10개의 `aiSuggest`를 읽어 글자 수 등을 계산했다. 글 본문은 Claude가 쓴 임의의 생활 글이라 제안이 쓸 만한지(품질)는 판단하지 않았다.

| 지표 | 결과 | 기준 | 판정 |
|---|---|---|---|
| 생성 성공 | 10/10(GitHub 실행 #17 한 번에) | 95% 이상 | 충족(표본 10건) |
| 요약 120자 초과 | 0건(72~87자, 평균 77.7자) | 0건 | 충족 |
| 요약 80자 안팎(70~90자) | 10/10 | 참고 | 충족. 5.1.1절의 Gemini 8편은 4/8이지만 모델이 달라 개선이라 단정하지 않는다 |
| 태그 3~5개 | 10/10(모두 5개) | 3~5개 | 충족 |
| 제목 후보 3개 | 10/10 | 3개 | 충족 |
| 후보 중 원제와 같은 것 | 0건 | 0건 | 충족. 다만 10개 원제가 모두 같은 `[테스트용] 임시 제목`이라 효과 판정은 약하다 |
| 제안을 만든 모델 | 10/10 `claude-sonnet-5-5` | 참고 | 지금까지 수락률은 Gemini 기준이라 Claude 기준 수락률은 아직 없다 |

**공개 글 상태 점검(같은 날 같은 방법):** 공개 글 16개 중 제안 도착(`ready`) 15개, AI 요청 없음(`none`) 1개, 반영(`applied`)·무시(`dismissed`)가 끝난 글 0개. 시연 글 10개와 체험용 4번은 모두 `ready`로 남아 있다. 반영·무시 기록(`aiFeedback`)이 남아 있는 글이 3개 있으나 상태는 `ready`다.

**주의:** 하늘님이 보고한 반영·무시 시험(15장 16번)의 대상 글은 이 점검으로 찾지 못했다. 비공개·휴지통 글은 공개 읽기로 보이지 않고, 시험 뒤 되돌렸을 수도 있다. 어느 쪽인지는 확인하지 못했다.

**5.2 고객** AIPM 수강생이자 관리자 1인(1순위). 수업 직후 글을 빨리 발행하고 나중에 복습하려고 찾는다.
**5.3 용어·메시지** 화면 용어는 「AI 제안」으로 통일, 카피 "AI가 제안해요, 선택은 내가 해요".

### 6.1 핵심 기능 (AI 제안)
| ID | 기능 | 동작 | 완료 기준 (Given / When / Then) |
|---|---|---|---|
| F1 | 제안 요청 | 글쓰기·수정에서 「AI 제안 받기」(새 글은 기본 켜짐, 수정은 기본 꺼짐) | 공개 글을 AI 체크로 저장하면 `aiStatus=pending`, 체크 해제하면 `none`. 비공개 글은 배치가 건너뛴다 |
| F2 | 제안 생성 | GitHub Actions 배치가 AI 호출. 예약(5분 간격 설정)은 실제로 실행된 적은 있으나(#9) 약 15시간에 1회라 보장하지 않으며, 확실한 방법은 글 상세 「지금 AI 제안 받기」 링크로 여는 수동 실행(`Run workflow`) | `pending` 공개 글에 요약·제목 3개·태그 3~5개를 만들어 `ready`로 저장. 휴지통 글은 건너뜀. 제안은 `ai*` 필드에만 쓰고 `title`·`summary`·`tags`는 건드리지 않음. 제공자는 `AI_PROVIDER`(기본 gemini, 또는 claude)로 고르고, claude 키가 없거나 호출이 HTTP 401·402·403·429·529로 실패하면 같은 실행에서 Gemini로 복귀(`AI_FALLBACK=off`면 끔). 응답 형식 오류 같은 글 내용 문제는 복귀하지 않고 F4 재시도로 처리. 제목 후보 중 원제와 같은 것은 제거(`dropSameTitles`, 전부 같으면 유지) |
| F3 | 확인·반영 | 제안 카드에서 항목별 선택, **클릭 시에만** 변경 | 반영 전에는 글이 그대로. 반영하면 선택 항목만 바뀌고 `aiStatus=applied`, 항목별 `aiFeedback`(accepted/edited/ignored) 기록. 무시하면 글은 그대로, `dismissed` |
| F4 | 실패 처리 | 1회 재시도 후 `failed`, 「직접 입력」 안내 | 응답 형식 오류·요약 120자 초과면 재요청 힌트로 1회 재시도. 그래도 실패하면 `failed`와 사유(`aiError`) 저장, 카드는 직접 입력 안내만 보이고 반영 버튼 없음 |
| F5 | 상한 | 하루 20건(한국시간 기준 초기화), 텍스트 6,000자, 이미지 제외 | 상한 초과분은 `pending`으로 남고 다음 날 처리. 이미지만 있는 글은 호출 없이 `failed` |

시나리오: 글 저장 → 대기 카드의 「지금 AI 제안 받기」로 배치를 수동 실행(약 1분 이내) → 제안 카드 표시 → 요약 수락, 제목은 고쳐서 수락, 태그는 무시 → 갤러리·검색·미리보기에 반영.

## 7. 데이터·상태 명세
**7.1 상태 `aiStatus`**

| 값 | 의미 | 다음 상태 |
|---|---|---|
| `none` | AI 제안 요청 안 함(기존 글 포함) | 수정에서 AI 체크 → `pending` |
| `pending` | 배치 대기 | `ready` 또는 `failed` |
| `ready` | 제안 도착, 관리자 결정 대기 | `applied` 또는 `dismissed` |
| `failed` | 생성 실패(`aiError`에 사유) | 수정에서 AI 체크 → `pending` |
| `applied` | 하나 이상 반영됨(`aiFeedback`, `aiAppliedAt` 기록) | 수정에서 AI 체크 → `pending` |
| `dismissed` | 무시함 | 수정에서 AI 체크 → `pending` |

**7.2 필드 (컬렉션 `posts`)**

| 필드 | 형식 | 쓰는 주체 | 설명 |
|---|---|---|---|
| `title`·`summary`·`tags`·`content`·`contentFormat`·`cover`·`visibility`·`authorUid`·`createdAt` | 기본 글 | 관리자 | 글 본체 |
| `summaryAuto` | boolean | 관리자 화면 | 요약이 본문 앞 60자 자동 대체인지(AI 요약을 반영하면 `false`로 갱신, v1.6) |
| `aiStatus`·`aiError` | string | 화면(요청), 배치(결과) | 7.1 |
| `aiSuggest` | map {summary, tags[], titles[], model, at} | **배치만** | 제안 본문, 사용 모델, 생성 시각 |
| `aiFeedback` | map {summary, tags, title} 각 accepted\|edited\|ignored | 관리자 화면 | 수락률 계산 원천 |
| `aiAppliedAt` | timestamp | 관리자 화면 | 반영 시각 |
| `trashed`·`trashedAt`·`prevVisibility` | boolean·timestamp·string | 관리자 화면 | 휴지통 7.3 |
| `updatedAt` | timestamp | 관리자 화면 | 수정 시각 |

**7.3 휴지통:** 이동 = `{trashed:true, trashedAt, prevVisibility:<이전>, visibility:"private"}`. 복구 = `{trashed:false, trashedAt 삭제, visibility:<prevVisibility>, prevVisibility 삭제}`. 영구삭제 = 문서 삭제(복구 불가).
**7.4 배치 규칙:** `aiStatus=pending`이고 비공개·휴지통이 아닌 글만 처리. `ai*` 필드 외에는 쓰지 않음. 하루 20건, 6,000자, 요약 120자 초과면 재시도 1회.
**7.5 수락률 계산:** 분모=결정이 끝난 글(`applied`·`dismissed`)의 요약·제목 항목 수, 분자=`accepted`+`edited`. 태그는 별도 보고.

## 8. 비기능적 요구사항
- **보안:** AI 키·서비스 계정은 GitHub Secrets에만 보관하고 로그에 출력하지 않는다. AI 결과는 `esc()`로만 화면에 넣는다. 글쓰기·수정·삭제는 관리자만 가능하고, 평가자 계정(F10)은 자기가 쓴 공개 글의 생성·수정만 가능하며 삭제·휴지통은 불가(모두 규칙으로 강제, 규칙 시뮬레이터 7건 확인).
- **성능·지연:** 제안 도착 시점은 예약 실행에 달려 있다. 예약은 약 15시간에 1회(#9)만 실행돼 지연이 클 수 있고, 수동 실행하면 약 1분 안에 도착한다(실행 20~50초 측정).. 관리자 1인이라 동시 접속 부담 없음.
- **개인정보:** 임시저장은 이 브라우저에만 저장. 나만보기·휴지통 글은 AI에 보내지 않는다.
- **접근성:** 본문·버튼 대비 4.5:1 이상(디자인 지침 측정값), 버튼 높이 44px 이상, 모바일 390px 가로 넘침 없음.
- **한계:** 휴지통 15일 삭제는 예약 실행이 아니라 관리자가 접속할 때 실행된다. 비관리자의 쓰기 차단은 규칙으로 강제하며 시크릿 창에서 글쓰기가 안 되는 것을 하늘이 확인했다(캡처 없음). 자동 화면 점검은 가짜 Firebase를 쓰므로 보안 규칙 자체는 검증하지 못한다. 평가자 권한은 규칙 시뮬레이터로 따로 시험했고(테스트 보고서 v0.14 4-6장), 평가자 비밀번호가 약하다는 위험은 하늘님이 감수하기로 했다.

**이 PRD의 현재 한계(요약)**

- 문제 증거가 약하다(3.3절).
- 수락률은 Claude가 쓴 글 11편·사용자 1명 기준의 방향 확인이다(샘플 글은 현재 휴지통이라 공개 글은 6편).
- 시크릿 창·폰 확인은 캡처 없는 하늘 보고다.
- 효과 지표 M11·M12·G3는 미측정이다.
- 보안 규칙은 자동 점검 범위 밖이다.
- 제안 생성 시점은 불규칙한 예약(약 15시간에 1회) 또는 관리자의 수동 실행(대기 카드 링크)에 달려 있다. 자동 처리는 증명되지 않았고, 수동 실행은 관리자가 GitHub에 로그인돼 있어야 한다. 제목 중복 제거의 효과도 재측정 전이다.
- Claude는 글 1편(성공 1건)으로만 확인했다. 실제 키 만료·한도에 따른 Gemini 복귀는 가짜 응답으로만 시험했고 겪어 보지 못했다. 첫 시도 실패의 원인은 확정하지 못했고(길이 제한 추정), 제한을 올린 뒤 성공했다.

남은 일 4·16(평가자의 새 글 저장 확인), 12/3 삭제 결과 확인(15)이 끝나면 v1.19를 제출본으로 쓴다. 14는 후속 과제다(예약이 거의 안 도는 문제는 화면의 수동 실행 링크로 대응했다).
